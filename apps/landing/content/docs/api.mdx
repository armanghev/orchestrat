The Orchestrat server speaks JSON over HTTP. The dashboard, the CLI and the MCP bridge all use the routes on this page. Examples use `http://localhost:8801`.

Request and response shapes are Zod schemas in [`packages/protocol`](https://github.com/armanghev/orchestrat/tree/main/packages/protocol/src); treat them as the source of truth for field-level detail.

## Conventions

- **Prefixes.** Routes for people live under `/api/v1`. Routes for agents live under `/api/v1/agent`. A few public routes need no token; see [Public routes](#public-routes).
- **Status codes.** Creates return `201` and queued work returns `202`. Repository and integration deletes return `204` with no body. Everything else returns `200`.
- **IDs** are UUIDs, and timestamps are ISO 8601 strings.
- **Request IDs.** Every response has an `x-request-id` header, also echoed in error bodies.
- **Pagination.** List routes take `limit` (1–100, default 50) and an opaque `cursor`, and return `next_cursor` (`null` on the last page). Event lists use `after` instead of `cursor`. A malformed cursor returns `400 VALIDATION_ERROR`.
- **Optimistic concurrency.** Task writes send the task's current `expected_version`; a stale one returns `409 TASK_VERSION_CONFLICT` with `current_version` when known. Document writes send `base_revision`; a stale one returns `409 DOCUMENT_CONFLICT` with `current_revision` and `base_revision`. Successful writes bump the version.
- **Archived projects** stay readable; writes return `409 PROJECT_ARCHIVED`.

### Idempotency keys

Some creates require an `Idempotency-Key` header of 1–128 characters. Repeating a request with the same key returns the original response. Reusing the key for a different request returns `409 IDEMPOTENCY_CONFLICT`. A missing key returns `400 VALIDATION_ERROR`.

Keys are scoped to the caller (person or agent). Task and chat creation keys are also scoped to the branch, so one key on two branches creates two items. Merge keys are scoped to the person and the target branch.

The key is required on:

- task, comment and bulk task creation (people and agents)
- chat creation and chat messages (people and agents)
- handoffs (people and agents)
- `POST /api/v1/agent/hooks/lifecycle`
- `POST /api/v1/projects/:projectId/merges`

## Authentication

### People

People send an access token on every `/api/v1` route except the public ones:

```http
Authorization: Bearer orch_sess_<token>
```

Sign-up, sign-in and refresh return a session. Shapes are in [`packages/protocol/src/auth.ts`](https://github.com/armanghev/orchestrat/blob/main/packages/protocol/src/auth.ts):

```json
{
  "access_token": "orch_sess_…",
  "refresh_token": "orch_refresh_…",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_expires_in": 2592000,
  "user": {
    "user_id": "…",
    "email": "you@example.com",
    "full_name": "…",
    "is_instance_admin": true
  },
  "invited_project_id": null
}
```

The access token lasts 1 hour and the refresh token 30 days. Refreshing returns a new pair and retires the old refresh token. Presenting the previous refresh token more than 60 seconds after it was replaced ends the session, because it may have leaked. A session ends 90 days after sign-in, however often it is refreshed. Session responses carry `Cache-Control: no-store`.

| Method | Path                      | Auth    | Behavior                                                                                                                                                                                                       |
| ------ | ------------------------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET`  | `/api/v1/auth/instance`   | none    | `{ needs_setup, signup_mode }`: whether the server has no accounts yet, and `invite`, `open` or `closed`                                                                                                       |
| `POST` | `/api/v1/auth/signup`     | none    | `{ email, password, full_name, invite_token?, setup_token? }`; `201` with a session. The first account needs `setup_token` and becomes the instance admin. `invited_project_id` is set when an invite was used |
| `POST` | `/api/v1/auth/login`      | none    | `{ email, password }`; a session                                                                                                                                                                               |
| `POST` | `/api/v1/auth/refresh`    | none    | `{ refresh_token }`; a new session pair                                                                                                                                                                        |
| `POST` | `/api/v1/auth/revoke`     | none    | `{ refresh_token }`; ends that token's session, for when the access token has expired. `204` whether or not the token was valid                                                                                |
| `POST` | `/api/v1/auth/logout`     | session | Ends the current session; `204`                                                                                                                                                                                |
| `POST` | `/api/v1/auth/logout-all` | session | Ends every session of the account, including the current one, and revokes its CLI credentials; `204`                                                                                                           |
| `POST` | `/api/v1/auth/password`   | session | `{ current_password, new_password }`; `204`. Ends every other session and revokes the account's CLI credentials                                                                                                |

Emails are trimmed and lowercased, up to 320 characters. Passwords are 10 to 256 characters, and `full_name` 1 to 120. Sign-up follows `ORCHESTRAT_SIGNUP`: with `invite` (the default) it needs a valid, unused `invite_token`, which the sign-up uses up. See [Users and accounts](/docs/users).

| Code                    | Status | When                                                                                                          |
| ----------------------- | ------ | ------------------------------------------------------------------------------------------------------------- |
| `INVALID_CREDENTIALS`   | 401    | Wrong email or password at sign-in                                                                            |
| `REFRESH_TOKEN_INVALID` | 401    | The refresh token is unknown, expired, revoked or retired, or the session is too old                          |
| `SETUP_TOKEN_REQUIRED`  | 403    | The first sign-up has no setup token, or the wrong one                                                        |
| `SIGNUP_CLOSED`         | 403    | `ORCHESTRAT_SIGNUP` is `closed`                                                                               |
| `INVITE_REQUIRED`       | 403    | The invite token is missing while `ORCHESTRAT_SIGNUP` is `invite`, or it is invalid, used, revoked or expired |
| `PASSWORD_INCORRECT`    | 403    | The current password is wrong when changing it                                                                |
| `EMAIL_TAKEN`           | 409    | An account already has that email                                                                             |
| `RATE_LIMITED`          | 429    | See [Rate limits](#rate-limits)                                                                               |

A missing, expired or revoked access token returns `401 UNAUTHENTICATED`. A request for a project you can't access returns `403 PERMISSION_DENIED`. An agent token sent to a human route returns `401 AGENT_CREDENTIAL_INVALID`.

### Agents

Agents call routes under `/api/v1/agent` with exactly one `Authorization` header holding an agent token:

```http
Authorization: Bearer orch_agent_<token>
```

- An agent token belongs to one agent in one project. The server takes the agent and project from the token; IDs in paths and bodies never change them.
- Tokens are random, stored only as hashes, and returned once, when issued.
- A missing, malformed or unknown token returns `401 AGENT_CREDENTIAL_INVALID`. A revoked token, or a token of a revoked agent, returns `401 AGENT_CREDENTIAL_REVOKED` immediately.
- Agents name a branch with `X-Orchestrat-Branch-Id` or pin requests to a session with `X-Orchestrat-Session-Id`; see [Choosing a branch](#choosing-a-branch).

Agent tokens are minted in two ways: by the CLI's browser approval (below), or by a project owner or admin through [Agents and credentials](#agents-and-credentials).

### CLI browser approval

`orchestrat setup` uses these routes to get a CLI credential and then one agent token per integration.

| Method | Path                                                    | Auth           | Behavior                                                                                                                                                                                   |
| ------ | ------------------------------------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST` | `/api/v1/cli/authorization/attempts`                    | none           | Start an attempt; `201 { attempt_id, secret, expires_at }`. Attempts expire after 10 minutes                                                                                               |
| `POST` | `/api/v1/cli/authorization/attempts/:attemptId/approve` | session        | Approve with an empty JSON body, from the dashboard's `/cli/authorize?attempt=<attempt_id>` page                                                                                           |
| `POST` | `/api/v1/cli/authorization/attempts/:attemptId/deny`    | session        | Deny the attempt                                                                                                                                                                           |
| `POST` | `/api/v1/cli/authorization/attempts/:attemptId/poll`    | `{ secret }`   | `{ status }`: `pending`, `denied`, `expired`, or `approved` with a one-time `credential` (`orch_cli_…`). At most one poll per attempt every 2 seconds, otherwise `429`                     |
| `GET`  | `/api/v1/cli/setup/projects`                            | CLI credential | Projects the approving person can access: `{ projects: [{ id, name, organization_name }] }`                                                                                                |
| `GET`  | `/api/v1/cli/setup/project`                             | CLI credential | `{ project_id }`: the project the credential is bound to, or `null`                                                                                                                        |
| `POST` | `/api/v1/cli/setup`                                     | CLI credential | `{ project_id, integration }`; creates an agent and returns `{ project_id, integration, agent, credential }`, where `credential.token` is the agent token. Requires project owner or admin |
| `POST` | `/api/v1/cli/setup/disconnect`                          | CLI credential | `{ project_id, agent_ids, revoke_cli }`; revokes 1–5 agents, and the CLI credential itself when `revoke_cli` is `true`                                                                     |

`integration` is one of `codex`, `claude-code`, `cursor`, `antigravity` or `opencode`. The CLI credential is sent as `Authorization: Bearer orch_cli_…` and works only on the `/api/v1/cli/setup` routes. An invalid one returns `401 UNAUTHENTICATED`.

## Errors

Errors share one envelope:

```json
{
  "error": {
    "code": "PERMISSION_DENIED",
    "message": "You do not have access to this project.",
    "details": {},
    "request_id": "req_…"
  }
}
```

Schema validation failures return `400 VALIDATION_ERROR` with the validation `issues` in `details`; an oversized body returns `413 VALIDATION_ERROR`. Some codes add a `details.reason`, listed per area below.

| Code                                                                                                       | Status | Meaning                                                                                                                                                         |
| ---------------------------------------------------------------------------------------------------------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `UNAUTHENTICATED`                                                                                          | 401    | Missing or invalid session, CLI credential, or realtime or download ticket                                                                                      |
| `INVALID_CREDENTIALS`, `REFRESH_TOKEN_INVALID`                                                             | 401    | Wrong email or password; unusable refresh token. See [People](#people)                                                                                          |
| `SETUP_TOKEN_REQUIRED`, `SIGNUP_CLOSED`, `INVITE_REQUIRED`, `PASSWORD_INCORRECT`                           | 403    | Sign-up and password rules. See [People](#people)                                                                                                               |
| `AGENT_CREDENTIAL_INVALID`, `AGENT_CREDENTIAL_REVOKED`                                                     | 401    | Bad or revoked agent token                                                                                                                                      |
| `PERMISSION_DENIED`                                                                                        | 403    | No access, or the role is too low                                                                                                                               |
| `CLAIM_NOT_OWNER`                                                                                          | 403    | The claim belongs to another agent or session                                                                                                                   |
| `NOT_FOUND`, `AGENT_NOT_FOUND`, `AGENT_SESSION_NOT_FOUND`, `CLAIM_NOT_FOUND`, `BRANCH_NOT_FOUND`           | 404    | The resource doesn't exist or isn't visible to the caller                                                                                                       |
| `VALIDATION_ERROR`, `REPOSITORY_NOT_CONFIGURED`                                                            | 400    | Invalid request, or the Git provider isn't set up on this server                                                                                                |
| `CONFLICT`                                                                                                 | 409    | Generic conflict, often with `details.reason`; also a duplicate slug or email                                                                                   |
| `EMAIL_TAKEN`                                                                                              | 409    | An account already has that email                                                                                                                               |
| `ORGANIZATION_SLUG_TAKEN`                                                                                  | 409    | Another organization has the slug                                                                                                                               |
| `PROJECT_ARCHIVED`                                                                                         | 409    | Write to an archived project                                                                                                                                    |
| `IDEMPOTENCY_CONFLICT`                                                                                     | 409    | Idempotency key reused for a different request                                                                                                                  |
| `TASK_VERSION_CONFLICT`, `TASK_DEPENDENCY_CYCLE`                                                           | 409    | Stale `expected_version`; dependency would form a cycle                                                                                                         |
| `TASK_NOT_CLAIMABLE`, `TASK_ALREADY_CLAIMED`                                                               | 409    | The task can't be claimed or changed now; another session holds it                                                                                              |
| `AGENT_SESSION_CLOSED`, `AGENT_SESSION_STALE`                                                              | 409    | The session is closed, or its last heartbeat is more than 60 seconds old                                                                                        |
| `DOCUMENT_CONFLICT`, `DOCUMENT_EDIT_MISMATCH`, `DOCUMENT_ARCHIVED`                                         | 409    | Stale `base_revision`; an edit's `old_text` doesn't match exactly once; the document is archived                                                                |
| `ATTACHMENT_QUOTA_EXCEEDED`, `ATTACHMENT_UPLOAD_EXPIRED`                                                   | 409    | Project attachment quota reached; the upload expired                                                                                                            |
| `TASK_COMMENTS_UNREAD`, `WATCH_LIMIT`, `INVALID_STATUS_TRANSITION`, `BLOCKER_CYCLE`                        | 409    | Attention rules; see [Attention and handoffs](#attention-and-handoffs)                                                                                          |
| `BRANCH_ARCHIVED`, `BRANCH_MISMATCH`, `BRANCH_NAME_TAKEN`, `BRANCH_PREVIEW_STALE`, `BRANCH_DECISION_STALE` | 409    | Branch rules; see [Branch errors](#branch-errors)                                                                                                               |
| `REPOSITORY_AUTHORIZATION_INVALID`, `REPOSITORY_CONNECTION_EXISTS`, `INTEGRATION_IN_USE`                   | 409    | Repository and integration rules; see [Repository connections](#repository-connections)                                                                         |
| `RATE_LIMITED`, `WAIT_LIMIT`, `HANDOFF_CHAIN_LIMIT`, `HANDOFF_RATE_LIMITED`, `WAKE_LIMIT`                  | 429    | See [Rate limits](#rate-limits)                                                                                                                                 |
| `INTERNAL_ERROR`                                                                                           | 500    | Unexpected failure; `502` when a Git provider doesn't answer                                                                                                    |
| `DOCUMENT_CONTENT_UNAVAILABLE`, `STORAGE_UPLOAD_FAILED`                                                    | 503    | Object storage isn't configured or can't be reached. A failed storage call returns `502`, and an uploaded size that doesn't match the reservation returns `409` |

## Rate limits

Limits are fixed windows kept in the server's memory, one minute unless the table says otherwise. A limited request returns `429 RATE_LIMITED` with a `Retry-After` header and `details.retry_after_seconds`.

Limits per IP see the client's address only when the server trusts its reverse proxy; set `ORCHESTRAT_TRUST_PROXY_HOPS` behind one. See [Configuration](/docs/configuration#server).

| Scope                                                     | Limit                                                                                                              |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `POST /api/v1/auth/login`                                 | 20 a minute per IP, and 10 failed attempts per email in 15 minutes                                                 |
| `POST /api/v1/auth/signup`                                | 10 a minute per IP                                                                                                 |
| `POST /api/v1/auth/refresh`, `POST /api/v1/auth/revoke`   | 60 a minute per IP, shared                                                                                         |
| `POST /api/v1/auth/password`                              | 5 per person in 15 minutes                                                                                         |
| `POST /api/v1/cli/authorization/attempts`                 | 10 a minute per IP                                                                                                 |
| `POST /api/v1/cli/authorization/attempts/:attemptId/poll` | 120 a minute per IP. Polling one attempt more often than every 2 seconds also returns `429`, without `Retry-After` |
| Attachment uploads, downloads and deletes, avatar upload  | 120 a minute per person or agent token                                                                             |
| `GET /api/v1/avatars/:key`                                | 1,200 a minute per IP                                                                                              |
| Webhooks                                                  | 600 a minute per IP                                                                                                |
| New branches registered by an agent                       | 10 a minute per agent token                                                                                        |

The attention routes have their own limits: `WAIT_LIMIT` caps concurrent long-polls, and `HANDOFF_RATE_LIMITED`, `HANDOFF_CHAIN_LIMIT` and `WAKE_LIMIT` stop handoff and wake loops.

## Public routes

These routes take no session or agent token.

| Method | Path                                                   | Behavior                                                                                             |
| ------ | ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| `GET`  | `/health`, `/api/v1/health`                            | `{ "status": "ok" }` while the process is up                                                         |
| `GET`  | `/ready`, `/api/v1/ready`                              | `{ "status": "ready" }` after a database check, or `503 { "status": "not_ready" }`                   |
| `GET`  | `/api/v1/attachments/download?ticket=<ticket>`         | Streams an attachment. The ticket comes from a download request, is single-use, and lasts 60 seconds |
| `GET`  | `/api/v1/avatars/:key`                                 | An avatar image. The key is random and comes from a profile's `avatar_url`                           |
| `GET`  | `/api/v1/repository/callback/:provider`                | Git provider OAuth redirect; see [Webhooks and provider callbacks](#webhooks-and-provider-callbacks) |
| `POST` | `/api/v1/webhooks/:provider`                           | Git provider webhooks                                                                                |
| `GET`  | `/api/v1/realtime/projects/:projectId?ticket=<ticket>` | WebSocket upgrade with a realtime ticket; see [Realtime](#realtime)                                  |

The `instance`, `signup`, `login`, `refresh` and `revoke` auth routes are also public (see [People](#people)), and so are the CLI authorization `attempts` and `poll` routes (see [CLI browser approval](#cli-browser-approval)).

When the server serves the dashboard, every other `GET` outside `/api`, `/health` and `/ready` returns the dashboard's `index.html`, so client-side routes load directly.

## Tasks

| Method   | Path                                              | Behavior                                                            |
| -------- | ------------------------------------------------- | ------------------------------------------------------------------- |
| `POST`   | `/api/v1/projects/:projectId/tasks`               | Create a task. `Idempotency-Key` required                           |
| `GET`    | `/api/v1/projects/:projectId/tasks`               | List task cards with filters and cursor pagination                  |
| `GET`    | `/api/v1/tasks/:id`                               | One task card                                                       |
| `PATCH`  | `/api/v1/tasks/:id`                               | Update `title`, `description` or `priority` with `expected_version` |
| `POST`   | `/api/v1/tasks/:id/move`                          | Move to a status and position with `expected_version`               |
| `GET`    | `/api/v1/tasks/:id/comments`                      | List comments with cursor pagination                                |
| `POST`   | `/api/v1/tasks/:id/comments`                      | Add a Markdown comment. `Idempotency-Key` required                  |
| `GET`    | `/api/v1/tasks/:id/dependencies`                  | Tasks this task depends on, and tasks it blocks                     |
| `POST`   | `/api/v1/tasks/:id/dependencies`                  | Add a dependency with `expected_version`                            |
| `DELETE` | `/api/v1/tasks/:id/dependencies/:dependsOnTaskId` | Remove a dependency with `expected_version`                         |

- **Fields.** `id`, `project_id`, `branch_id`, `key`, `title`, `description`, `priority`, `status`, `position`, `version`, `created_by`, `created_by_user_id`, `created_at`, `updated_at`, `started_at`, `completed_at`, `cancelled_at`. Cards add `comment_count` and `unresolved_blocker_count`. `created_by` says whether a person or an agent created the task; the legacy `created_by_user_id` is `null` for agent-created tasks.
- **Values.** Priorities: `urgent`, `high`, `medium`, `low`, `none`. Statuses: `backlog`, `ready`, `claimed`, `in_progress`, `blocked`, `review`, `done`, `cancelled`. People can't select `claimed`; only the agent claim flow sets it.
- **Create** takes `title`, optional `description`, `priority` (default `none`) and `status` (default `backlog`). The task is appended to its status column.
- **List** takes `status`, `priority`, `limit` and `cursor`, ordered by `position` then ID. It returns `{ tasks, total, next_cursor }`, where `total` counts every match on the branch.
- **Move** takes `status`, optional `before_task_id` (an anchor in the target column) and `expected_version`. Entering `in_progress`, `done` or `cancelled` sets the matching timestamp; leaving the status clears it.
- **Comments** are immutable Markdown in `body_markdown`, with a per-task `sequence` and up to 20 `mentions`. Reads return `{ comments, next_cursor }`.
- **Dependencies** stay on one branch: a dependency on another branch's task returns `400 VALIDATION_ERROR` with `reason: "cross_branch"`. A self-edge or cycle returns `409 TASK_DEPENDENCY_CYCLE`.

## Presence and events

| Method | Path                                   | Behavior                                                                     |
| ------ | -------------------------------------- | ---------------------------------------------------------------------------- |
| `GET`  | `/api/v1/projects/:projectId/presence` | Every active agent: `online` or `offline`, current task, session `branch_id` |
| `GET`  | `/api/v1/projects/:projectId/events`   | Ordered project events; `limit`, `after`, `branch_id`, `all_branches`        |

- An agent is `online` when it has an active session with a heartbeat in the last 60 seconds. Its `branch_id` is its session's branch, or `null` when offline.
- Events are ordered by numeric event ID. Pass the previous response's `next_cursor` as `after`.
- Each event has a `branch_id`, or `null` for project-wide events (branches, repository, agents, credentials). A branch's list includes its own events plus the project-wide ones. `all_branches=true` returns every branch; the dashboard's realtime catch-up uses it to keep one cursor.

## Branches

Every project has branches, and exactly one is the default. Tasks (with comments, dependencies and claims), documents (with folders, revisions and attachments), chats (with participants and messages) and agent sessions belong to one branch. Organizations, projects, members, agents and credentials are project-wide. Project responses include `default_branch_id`. How branches work: [Architecture](/docs/architecture#branches).

### Choosing a branch

A request that names no branch uses the default branch, so clients written before branches keep working.

**People.** These routes take an optional `branch_id` query parameter:

- `GET` and `POST /api/v1/projects/:projectId/tasks`
- `GET` and `POST /api/v1/projects/:projectId/documents`
- `POST /api/v1/projects/:projectId/document-folders`
- `GET` and `POST /api/v1/projects/:projectId/chats`
- `GET /api/v1/projects/:projectId/inbox`
- `GET /api/v1/projects/:projectId/events`
- `POST /api/v1/projects/:projectId/handoffs`

A `branch_id` outside the project returns `404 BRANCH_NOT_FOUND`. Archived branches stay readable; a create on one returns `409 BRANCH_ARCHIVED`. Routes for a single task, document, attachment or chat take the branch from that item. Presence, message candidates and the human attention routes are project-wide.

**Agents.** Agent routes resolve the branch in this order:

1. **Pinned session.** `X-Orchestrat-Session-Id: <session id>` uses that session's branch. A claim uses the session in its body. If `X-Orchestrat-Branch-Id` names a different branch, the request fails with `409 BRANCH_MISMATCH`. A session that isn't the agent's returns `404 AGENT_SESSION_NOT_FOUND`.
2. **Header.** `X-Orchestrat-Branch-Id: <branch id>`.
3. **The default branch.**

Both headers must be UUIDs; a malformed value returns `400 VALIDATION_ERROR` with `details.header`. Agents can read tasks, documents and chats on any branch by ID. A write to an item on a different branch than the one named or pinned returns `409 BRANCH_MISMATCH`; a write with no branch signal uses the item's branch.

New branch error codes go only to requests that name a branch (`?branch_id=`, `X-Orchestrat-Branch-Id` or `X-Orchestrat-Session-Id`) and to the branch, merge, decision and repository routes. Other requests get an existing code with a `details.reason`:

| Failure                                         | Response                                              |
| ----------------------------------------------- | ----------------------------------------------------- |
| Claim a task on another branch than the session | `409 TASK_NOT_CLAIMABLE`, `reason: "branch_mismatch"` |
| Claim a task on an archived branch              | `409 TASK_NOT_CLAIMABLE`, `reason: "branch_archived"` |
| Write to an item on an archived branch          | `409 CONFLICT`, `reason: "branch_archived"`           |
| Reference an item on another branch             | `400 VALIDATION_ERROR`, `reason: "cross_branch"`      |

Cross-branch references are task dependencies, blocking tasks, the task in a handoff, and `document_ids` in chat messages.

### Branch routes

| Method | Path                                                        | Who         | Behavior                                                                                                                                  |
| ------ | ----------------------------------------------------------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `GET`  | `/api/v1/projects/:projectId/branches`                      | member      | Active branches, default first, then most recently updated. `include_archived=true`; `name` filters by exact name                         |
| `POST` | `/api/v1/projects/:projectId/branches`                      | member      | `{ name }`; `201 { branch }`. `409 BRANCH_NAME_TAKEN` when an active branch has the name                                                  |
| `GET`  | `/api/v1/projects/:projectId/branches/:branchId`            | member      | `{ branch }`                                                                                                                              |
| `POST` | `/api/v1/projects/:projectId/branches/:branchId/default`    | owner/admin | Make it the default. `409 BRANCH_ARCHIVED` for an archived branch                                                                         |
| `POST` | `/api/v1/projects/:projectId/branches/:branchId/archive`    | owner/admin | Archive: read-only, hidden by default, nothing deleted, agent sessions closed. `409 CONFLICT`, `reason: "default_branch"` for the default |
| `POST` | `/api/v1/projects/:projectId/branches/:branchId/onboarding` | member      | `{ "choice": "blank" }` finishes the branch's setup. `409 CONFLICT`, `reason: "onboarding_completed"` when already done                   |

A branch is `{ id, project_id, name, is_default, name_source, created_via, created_by, onboarding_state, onboarding_choice, archived_at, archived_reason, provider, open_decision_count, created_at, updated_at }`. `provider` is `null` without a connected repository, otherwise `{ provider, state, head_sha }` with `state` `tracked`, `missing` or `untracked`. `archived_reason` is `provider_deleted`, `manual` or `replaced_on_connect`.

Branch names are 1–255 characters and follow a subset of `git check-ref-format`: no spaces, control characters or `~ ^ : ? * [ \`; no leading `-` or `/`; no trailing `/` or `.lock`; no `..`, `//` or `@{`; and not `@`. Names are unique among active branches only.

### Imports, merges and decisions

People only. Agents can't archive, merge, import, set the default or resolve decisions.

| Method | Path                                                        | Who                   | Behavior                                                                                                                                                                   |
| ------ | ----------------------------------------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST` | `/api/v1/projects/:projectId/merges/preview`                | member or owner/admin | `{ source_branch_id, target_branch_id, kind, selection? }`; `{ preview }`                                                                                                  |
| `POST` | `/api/v1/projects/:projectId/merges`                        | member or owner/admin | `Idempotency-Key` required. `{ source_branch_id, target_branch_id, kind, selection?, choices, preview_fingerprint, archive_source?, complete_onboarding? }`; `201 { run }` |
| `GET`  | `/api/v1/projects/:projectId/merges`                        | member                | `branch_id` (source or target), `limit`, `cursor`; `{ runs, next_cursor }`, newest first                                                                                   |
| `GET`  | `/api/v1/projects/:projectId/decisions`                     | member                | `branch_id` (target), `status`; `{ decisions }`, newest first                                                                                                              |
| `POST` | `/api/v1/projects/:projectId/decisions/:decisionId/resolve` | owner/admin           | `{ choice }` with `use_source` or `use_target`; `{ decision }`                                                                                                             |

- **Who.** `kind` is `import` or `merge`. Members import into any branch except the default. A merge, an import into the default branch, and `archive_source: true` need an owner or admin, for the preview as well as the apply.
- **Selection.** An import takes `{ tasks, documents, chats }`, each `"all"` or a list of up to 2,000 lineage keys. A merge always takes everything. Selecting a task also brings the tasks it depends on that the target lacks.
- **Preview.** Each item has an `outcome`: `copy`, `apply`, `unchanged`, `keep_target`, `conflict` or `skipped`, plus its fields and both sides' values. `counts` totals outcomes per item type, and `fingerprint` covers every version the apply depends on.
- **Apply.** The apply re-plans under the project lock. If the fingerprint no longer matches `preview_fingerprint`, it returns `409 BRANCH_PREVIEW_STALE` with the new preview in `details.preview`. An import must choose `use_source` or `use_target` in `choices` for every conflict, otherwise `400 VALIDATION_ERROR` with `reason: "missing_choice"`.
- **Merges never ask.** A conflict keeps the target's version and becomes a decision. A task with an active claim on the target is never changed.
- **Limits.** A run takes at most 2,000 top-level items, 20,000 comments and messages, and 5 GiB of attachments (`400 VALIDATION_ERROR`, `reason: "too_large"`). The source and target must differ (`reason: "same_branch"`). Copied attachments count toward the project quota and need object storage.
- **Events.** A run emits one `merge.import_applied` or `merge.merge_applied` event on the target branch, plus `decision.opened` when it created decisions.
- **Resolving.** `use_target` keeps the target and records the source state as agreed. `use_source` applies the recorded source values if the target hasn't changed since; otherwise `409 BRANCH_DECISION_STALE` with the refreshed decision in `details.decision`. `use_source` on a claimed task returns `409 TASK_ALREADY_CLAIMED`, and a settled decision returns `409 CONFLICT` with `reason: "decision_closed"`.

A run has `trigger` `dashboard` or `provider_merge`, and a fork merge is recorded with `status: "skipped"` and `skip_reason: "fork"`. A decision has `reason` `changed_on_both`, `added_on_both`, `path_collision` or `target_claimed`, and `status` `open`, `resolved_source`, `resolved_target` or `superseded`.

- `{ "mode": "rename_default" }` (the default) renames the default branch to `D`. Another active branch named `D` is archived with reason `replaced_on_connect`; its work stays importable.
- `{ "mode": "use_existing", "branch_id": "…" }` makes the active branch named `D` the default; the old default stays an ordinary branch.

`create_existing_branches` (default `false`) also creates branches for the provider's other branches; otherwise each one gets a branch on its first push.

## Realtime

```text
POST /api/v1/realtime/tickets   { "project_id": "…" }
  -> { "ticket": "…", "expires_at": "…" }
GET  ws://localhost:8801/api/v1/realtime/projects/<projectId>?ticket=<ticket>
```

- A ticket needs a session token and project membership. It is single-use, bound to one project, and valid for 45 seconds. Behind TLS, use `wss://`.
- The socket sends one envelope per event: `project_id`, `branch_id` (when the event has one), `sequence`, `event_type`, `entity_type`, `entity_id`, and `actor`. Chat events can add `message_id`, `mentions` and `affected_participant`.
- `entity_type` is one of `chat`, `project`, `task`, `claim`, `agent`, `credential`, `session`, `document`, `hook`, `run`, `branch`, `merge`, `decision` or `repository`.
- The socket is server-to-client only; a client message closes it. After a reconnect, read `GET /api/v1/projects/:projectId/events` with `after` set to the last `sequence` you saw.

## Agent API

Every route in this section is under `/api/v1/agent` and needs an agent token. Paths below are relative to that prefix.

### Agent sessions and events

| Method | Path                             | Behavior                                                                                                |
| ------ | -------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `GET`  | `/project`                       | The token's project, with `default_branch_id`                                                           |
| `POST` | `/sessions`                      | `{ runtime, integration, external_session_id?, branch_id? }`; open a session                            |
| `POST` | `/sessions/:sessionId/heartbeat` | Refresh the session and renew its active claim leases                                                   |
| `POST` | `/sessions/:sessionId/close`     | Close the session and revoke its active claims                                                          |
| `POST` | `/hooks/lifecycle`               | `{ event, session_id, runtime, integration, external_session_id?, error? }`. `Idempotency-Key` required |
| `GET`  | `/presence`                      | Presence for the project (backs the MCP `list_agents` tool)                                             |
| `GET`  | `/events`                        | Project events; `limit`, `after`                                                                        |

- A session opens on `branch_id`, else the header's branch, else the default branch, and returns its `branch_id`. Opening one on an archived branch returns `409 BRANCH_ARCHIVED`.
- A session is stale when its last heartbeat is more than 60 seconds old. Heartbeats and claims on a stale session return `409 AGENT_SESSION_STALE`; closing is still allowed.
- Lifecycle `event` is `session.started`, `session.ended` or `run.failed`. The branch travels in `X-Orchestrat-Branch-Id`. `session.started` for a session that already exists on another branch returns `409 AGENT_SESSION_CLOSED` with `reason: "branch_mismatch"`. `session.ended` also closes the agent's other active sessions with the same `external_session_id`.

### Agent tasks and claims

| Method  | Path                                   | Behavior                                                                                        |
| ------- | -------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `GET`   | `/tasks`                               | List tasks; `status`, `priority`, `limit`, `cursor`                                             |
| `POST`  | `/tasks`                               | Create a `backlog` or `ready` task. `Idempotency-Key` required                                  |
| `POST`  | `/tasks/bulk`                          | `{ tasks }`: create 1–50 tasks in one all-or-nothing batch. `Idempotency-Key` required          |
| `PATCH` | `/tasks/bulk`                          | `{ tasks }`: edit or move 1–50 distinct tasks (each with `task_id`) in one all-or-nothing batch |
| `GET`   | `/tasks/:id`                           | One task                                                                                        |
| `PATCH` | `/tasks/:id`                           | Edit metadata or move an unclaimed task, with `expected_version`                                |
| `GET`   | `/tasks/:id/comments`                  | Read comments from people and agents                                                            |
| `POST`  | `/tasks/:id/comments`                  | Add a Markdown comment. `Idempotency-Key` required                                              |
| `POST`  | `/tasks/:id/claim`                     | `{ session_id, lease_seconds? }`; claim a `ready` task                                          |
| `POST`  | `/sessions/:sessionId/claims/release`  | `{ claim_token, acknowledged_through? }`; return the task to `ready`                            |
| `POST`  | `/sessions/:sessionId/claims/complete` | `{ claim_token, acknowledged_through? }`; move the task to `done`                               |
| `POST`  | `/sessions/:sessionId/claims/status`   | Set `in_progress`, `blocked` or `review` on an owned claim, using its claim token               |

- **Claims** need an active session on the task's branch, a `ready` task and resolved dependencies. `lease_seconds` defaults to 300 and accepts 30–86,400. The response holds the claim and a `claim_token`; only the owning agent and session can release or complete it. Expired leases are reconciled when tasks are read or claimed. Concurrent claims produce one winner; the other gets `409 TASK_ALREADY_CLAIMED` with the active claim's lease details.
- **Updates** take `title`, `description`, `priority`, `status`, optional `acknowledged_through` and required `expected_version`, applied as one version bump. A status change follows the human move rules and is refused with `409 TASK_NOT_CLAIMABLE` while the task has an active claim: `reason` is `own_claim` when the caller holds it (use the claim routes instead), otherwise `claimed`. Moving to `review` or `done` applies the unread-comments guard.
- **Bulk** routes run in one transaction: any failure applies nothing and returns the single-item error with `details.index` and the item's `task_id` (update) or `title` (create). Results come back in input order, and each task emits the same events as the single route.

### Agent branches

| Method | Path                  | Behavior                                                                                                                               |
| ------ | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `GET`  | `/branches`           | `include_archived`, `name`; `{ branches }`                                                                                             |
| `GET`  | `/branches/:branchId` | `{ branch }`                                                                                                                           |
| `POST` | `/branches/register`  | `{ name, git_default_branch?, head_sha?, force_new? }`; `{ branch, created }`. Returns the active branch with that name, or creates it |

`register` refuses to revive a branch the provider deleted: when only archived branches have the name and the newest was deleted on the provider, it returns `409 BRANCH_ARCHIVED` with `branch_id` and `archived_at`, and `force_new: true` creates a new branch anyway. `git_default_branch` is the checkout's `origin/HEAD` branch; it renames the default branch when that is still the fallback `main`, no repository is connected, and no active branch has the name. Creating more than 10 branches a minute per agent token returns `429 RATE_LIMITED`; registering an existing branch is never limited.

## Not implemented

The API has no routes for:

- deleting tasks, or editing and deleting comments
- remote MCP or MCP OAuth
- agent capability matching or auto-assignment
- syncing documents with a local filesystem, or collaborative cursors
