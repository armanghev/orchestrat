Storage is optional. Without it, Orchestrat keeps everything in Postgres and documents work normally, but attachments and avatar uploads are off. Add an S3-compatible bucket when you want them.

## What storage holds

| Data               | Without storage                                 | With storage                                                                                                        |
| ------------------ | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Document revisions | Stored in Postgres.                             | Each new revision is also written to the bucket and read back from it, checked against its stored size and SHA-256. |
| Attachments        | Off. Uploads fail with `STORAGE_UPLOAD_FAILED`. | Files attached to documents: images you add in the dashboard editor and files agents upload with the CLI.           |
| Avatars            | Off.                                            | Profile pictures uploaded in onboarding and profile settings.                                                       |

Revisions written before you added storage stay in Postgres and keep working. Once storage is on, keep it on: the server reads newer revisions from the bucket and returns `DOCUMENT_CONTENT_UNAVAILABLE` when it can't reach them.

Objects live under two prefixes in the bucket: `document-revisions/v1/` and `document-attachments/v1/`. Deleting a project deletes its objects. Branch imports and merges copy attachment objects on the server.

## How uploads work

Attachment bytes never pass through the Orchestrat server on the way in:

1. The dashboard or CLI asks the server for an upload. The server checks permissions and the project quota.
2. The server returns a presigned `PUT` URL for the bucket, valid for 15 minutes.
3. The client uploads the file straight to that URL. Files over 100 MiB are sent as a multipart upload in 16 MiB parts.
4. The client tells the server the upload is complete, and the server checks the stored object's size.

Each attachment can be up to 2 GiB. Downloads go through the server, so the bucket never serves files to browsers directly.

## Reachable endpoint

Upload URLs point at `ORCHESTRAT_S3_ENDPOINT`. Every browser that uses the dashboard and every machine where agents run the CLI must be able to reach that address, not only the Orchestrat server.

<Callout type="warn" title="Use an address browsers can resolve">
  With MinIO on your own machine, browsers reach it at `http://localhost:9000`.
  A compose service name such as `http://minio:9000` only resolves inside the
  compose network, so uploads from the dashboard fail. On a server, give the
  storage endpoint a public hostname, such as
  `https://s3.orchestrat.example.com`.
</Callout>

Orchestrat uses path-style URLs: `<endpoint>/<bucket>/<object key>`. If you put a reverse proxy in front of your storage, it must pass those paths through unchanged.

## MinIO with compose

The compose file has an optional `storage` profile that runs MinIO, creates the bucket and applies the CORS rule. Set the storage variables in `.env`:

```bash
ORCHESTRAT_S3_ENDPOINT=http://localhost:9000
ORCHESTRAT_S3_REGION=us-east-1
ORCHESTRAT_S3_BUCKET=orchestrat
ORCHESTRAT_S3_ACCESS_KEY_ID=<MinIO access key>
ORCHESTRAT_S3_SECRET_ACCESS_KEY=<MinIO secret key>
```

Then start everything with the profile:

```bash
docker compose --profile storage up -d
```

Keep passing `--profile storage` on later `up` commands, or MinIO doesn't start.

## Amazon S3

Create a private bucket and an IAM user or role for Orchestrat, then set:

```bash
ORCHESTRAT_S3_ENDPOINT=https://s3.us-east-1.amazonaws.com
ORCHESTRAT_S3_REGION=us-east-1
ORCHESTRAT_S3_BUCKET=orchestrat-example
ORCHESTRAT_S3_ACCESS_KEY_ID=<access key ID>
ORCHESTRAT_S3_SECRET_ACCESS_KEY=<secret access key>
```

The calls Orchestrat makes need this policy on the bucket:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:ListBucketMultipartUploads"],
      "Resource": "arn:aws:s3:::orchestrat-example"
    },
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject",
        "s3:AbortMultipartUpload",
        "s3:ListMultipartUploadParts"
      ],
      "Resource": "arn:aws:s3:::orchestrat-example/*"
    }
  ]
}
```

## Cloudflare R2

Create a bucket and an R2 API token with **Object Read & Write** on it, then set:

```bash
ORCHESTRAT_S3_ENDPOINT=https://<account id>.r2.cloudflarestorage.com
ORCHESTRAT_S3_REGION=auto
ORCHESTRAT_S3_BUCKET=orchestrat
ORCHESTRAT_S3_ACCESS_KEY_ID=<R2 access key ID>
ORCHESTRAT_S3_SECRET_ACCESS_KEY=<R2 secret access key>
```

R2's region is always `auto`. Use the account endpoint without the bucket name in the path; set the bucket in `ORCHESTRAT_S3_BUCKET`. The server refuses to start when the endpoint includes a bucket path.

## Avatars

Avatars (JPEG, PNG or WebP, up to 2 MiB) are uploaded through the Orchestrat server, which writes them to storage. Browsers then load them from `ORCHESTRAT_S3_PUBLIC_URL`, so avatar images must be publicly readable at that URL. Document revisions and attachments must stay private: never make the whole bucket public.

## CORS

Because browsers upload straight to the bucket, the bucket needs a CORS rule that lets your Orchestrat origin send `PUT` requests with a `Content-Type` header. No `GET` rule is needed, because downloads go through the server. Set the allowed origin to your `ORCHESTRAT_PUBLIC_URL`:

```json
[
  {
    "AllowedOrigins": ["https://orchestrat.example.com"],
    "AllowedMethods": ["PUT"],
    "AllowedHeaders": ["Content-Type"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3600
  }
]
```

- **Cloudflare R2:** paste the rule into the bucket's **Settings → CORS policy**.
- **Amazon S3:** paste it into the bucket's **Permissions → Cross-origin resource sharing (CORS)**. With the AWS CLI, wrap the array as `{"CORSRules": [...]}` and run `aws s3api put-bucket-cors --bucket orchestrat-example --cors-configuration file://cors.json`.
- **MinIO with the `storage` profile:** already applied.

If you change `ORCHESTRAT_PUBLIC_URL`, update the rule. Uploads from an origin that isn't listed fail in the browser before they reach the bucket.

## Attachment quota

Each project can store up to `ORCHESTRAT_ATTACHMENT_QUOTA_BYTES` of attachments, 10 GiB by default. The total counts finished attachments, uploads in progress and copies made by branch imports and merges. An upload that would go over the limit fails with `ATTACHMENT_QUOTA_EXCEEDED`.

```bash
# 50 GiB per project
ORCHESTRAT_ATTACHMENT_QUOTA_BYTES=53687091200
```

## Back up the bucket

Once storage is on, a Postgres backup alone is not a complete backup: newer document revisions and every attachment live in the bucket. Back up the bucket together with the database, and restore them together. See [Upgrades and backups](/docs/upgrades).
